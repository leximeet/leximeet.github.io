# 发布与版本管理

Desktop、Desktop Core、Browser 与 LMCP 的首次正式版本及 Git 标签统一为 **`1.0.0`**。组织首页和文档站随这组版本更新内容，不单独打产品标签；Dictionary 继续使用已发布的 `v0.0.3` 词包和 `release.json`，不随应用重打标签。

## 推送前完成的检查

1. 工作区干净，产品版本与锁文件一致；Core实际提交等于Desktop gitlink。
2. LMCP规范原字节、逐文件摘要、两端冻结与来源一致；同步DTO和业务适配，不能只替换摘要字符串。
3. 运行各仓格式、文档、类型/单元/集成检查，再串行运行隔离的真实生产UI、连接、安装载荷检查。
4. 正式安装载荷和扩展包的版本与来源可核对，保留SHA-256、许可和对应源码；原始测试资料不进入仓库。
5. 核对Actions语法、固定依赖与可干净构建性；本地成功不等于远端工作流已经成功。

测试必须使用专用资料、回环端口和无头浏览器，不使用日常浏览器、系统剪贴板或修改系统日期。模拟时钟只作用于隔离测试环境。

## 发布顺序

Desktop依赖Core的精确提交，不能先推Desktop再让CI等待一个尚不存在的gitlink。推荐顺序是 **LMCP → Core → Browser → Desktop → 组织与文档站**；四个 `1.0.0` 产品标签指向各仓核验过的当前结果提交。

## 首次公开历史与来源

本轮六仓的公开 main 保留两条提交：各仓远端原始 `init commit`，以及直接以该 init 为父提交的当前结果提交。原始 init 的 SHA、作者和提交时间保持不变；后续开发提交压缩进结果提交，不用孤立根提交替换远端 init。Dictionary 已发布的资源历史不属于本轮六仓整理范围。

整理前保存完整开发历史、备份分支与私有 Git bundle，并核对可以恢复；这些备份不推送到公开仓。公开前审查结果树、提交信息和需推送的引用，排除个人环境路径、过程报告、测试资料和凭据。只推送审核后的 main 与各软件仓的 `1.0.0` 标签，不使用 `git push --all` 或 `git push --tags` 批量公开备份历史及旧候选标签。

推送前再次核对远端 main 仍为已确认的原始 init，结果提交应可从它正常快进。远端若出现其他提交，停止并重新审查；此规则不授权覆盖远端历史。推送、创建 Release、商店提交和 Pages 部署均需维护者明确授权。

正式来源以各仓 `1.0.0` 标签、消费端冻结清单、Desktop 的 Core gitlink 和发行物附带的源码、构建、发布 manifest 为准；安装载荷使用 `BUILD-MANIFEST.json` 核对实际物料。正式结果提交生成前，不预写它的 SHA；历史候选报告保留当时的版本、源码与验收事实，标明历史范围，不能改写成新结果提交的验证。后续 main 变化不应使已发布物料的来源漂移。

标签和源码推送不等于分发平台已经发布。main推送触发自动检查；Desktop安装载荷、跨仓连接与Browser真实包替换等工作流按各仓说明人工触发。GitHub Release、浏览器商店和Pages部署由维护者审阅后分别执行。

## 1.0.0之后的资料保护

正式1.0.0起维护真实用户资料的升级承诺。后续结构变化需要明确版本、迁移或安全拒绝策略，以及备份、重开、升级与恢复测试；禁止为了通过测试清空旧正式库。首发前的0.x/rc试验库不是已承诺兼容的正式格式，遇到不识别的资料应保留原文件并提示独立工作区。

连接后的浏览器仍封存独立资料A，使用桌面B+C，明确断开恢复A。账号和独立设备云同步属于2.0.0，不能把1.0.0本机连接称为云同步。

本页描述发布方法；具体平台、签名、公证、商店与远端检查状态，必须查看对应发行记录，不能从版本号推断。
